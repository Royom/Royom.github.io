Agent Token Efficiency重新审视

1. 可以做什么方面

层次 核心问题 典型方法
单次模型调用 一次输入或推理能否更短？ Prompt 压缩、短 CoT、推理预算
完整 Agent 任务 完成任务能否少读、少想、少调用工具、少重试？ 上下文管理、工具选择、早停、模型路由
Agent 系统执行 同样的任务能否消耗更少实际计算？ KV 缓存复用、调度、潜空间通信

第一个层面工作太多，第三个层面对底层技术的要求更高，因此优先选择中间这一层。

2. 更具体的目标/指标

在相同任务成功率下减少整条执行轨迹的成本，或者在相同总预算下提高成功率。

3. 发展历程

阶段 研究重心 代表工作及其意义
2022–2023：建立交互能力 思考、行动、观察、反思 ReAct 建立交替推理与行动范式；Reflexion 利用反馈和记忆改善后续尝试。主要目标是能力。
2023–2024：压缩输入、简化结构 减少冗余上下文，优化 Agent 计算图 LLMLingua 压缩输入；GPTSwarm 将 Agent 系统表示为可优化的计算图。
2024–2025：显式优化协作成本 减少通信边、参与者和交互轮次 AgentPrune，ICLR 2025、AgentDropout，ACL 2025 代表这一阶段。
2025–2026：把上下文管理变成决策 什么时候压缩、保留什么、何时恢复 ACON 根据失败优化压缩规则；AgentFold，ICLR 2026 主动折叠历史；AgentOCR，ACL 2026 探索用视觉表示压缩交互历史。
2026：联合考虑预算、失败和恢复 继续执行是否值得，省 Token 是否损害可靠性 EET，Findings ACL 2026 研究早停；CodeRescue，预印本 研究失败后继续廉价恢复还是升级模型。

5.当前存在的一些挑战

  • 压缩上下文后，Agent 可能重新调用工具获取被删信息；
  • 减少推理 token 后，可能增加重试次数；
  • 缩短 prompt 可能破坏 KV cache，实际成本反而上升；
  • 平均 token 降低，可能来自更早放弃困难样本；
  • 总 token 相同的两个系统，成功率、延迟和尾部成本可能完全不同。
  • Agent 缺少在线预算意识（bagen、LLM Agents Are Latent Context Managers）

一、整体方向

1.1 目标和几个容易混淆的指标

这里关心的不只是一次 Prompt 能压到多短，而是 Agent 跑完整个任务用了多少 Token、调用了多少次工具，以及最后有没有完成任务。理想情况是在成功率基本不变的前提下降低成本，或者在相同预算下提高成功率。

看具体方法时，可以关注三个方向：

  • 适用范围：需要改模型权重、Attention Mask，还是只改 Prompt、外部记忆和 Agent harness。前者通常只适用于开源模型，后者更容易接入闭源 API。
  • 成本口径：不能只看输出 Token 或单轮上下文长度，还要看累计输入、工具调用、重试次数，以及 prefix cache 的命中和失效。
  • 信息是否可恢复：摘要属于有损压缩，ID、URL、分页游标等细节容易丢；外部归档虽然多了一次读取，但原文还能找回。

二、降低上下文的重复处理成本

这一部分关注下一轮模型需要重新读取多少历史，以及修改上下文后需要重新计算多少内容。训练方式、决策者和是否使用旁路模型只作为每篇论文的实现差异，不再用于划分方向。

2.1 可恢复的活动工作集

这类方法缩小模型当前看到的内容，同时把原始内容保存在外部，需要时仍能恢复。

Codex 的实验性上下文管理

参考：Codex new_context 实现、Unrolling the Codex agent loop

Codex 在 2026 年加入了一套实验性的 context management 路径。它不是所有版本都默认用来替代 compaction，更准确地说，是在原有摘要压缩之外尝试“Token Budget + 新窗口 + 外部历史”的做法。

  1. 预算感知：模型能看到当前窗口还剩多少 Token，用它判断是否应该整理状态或切换窗口。
  2. 切换窗口：new_context 会开启一个新窗口，并明确不总结旧对话。
  3. 外部记录：History 用来查旧窗口，Notes 用来保存需要跨窗口延续的状态。

⭐LLM Agents Are Latent Context Managers: Eliciting Self-Managed Context via State Proprioception

比较有意思的地方：论文认为成熟模型可能已经有一定的上下文管理能力，只是它看不到每块内容用了多少 Token、多久没访问等状态。作者因此设计了 VISTA，把这些信息做成一个“状态仪表盘”，不训练模型，只增加接口。

实验设置

覆盖了几种不同长度的场景：

  1. LOCA-Bench：75 个任务配置，主要看百万 Token 级轨迹下的上下文压力。
  2. BrowseComp-Plus：使用 150 题子集，并把活动窗口压到 \(W=12\text{K}\)，看早期证据能否保留下来。
  3. GAIA：使用公开验证集中的 165 题，轨迹相对更短。
  4. AMA-Bench：208 个 Episode，用来测试离线轨迹记忆迁移。

评测用了 Gemini-3-Flash、Claude-Sonnet-4.5、DeepSeek-V4-Pro 和 GLM-5。论文的主要结果是 VISTA 在四个模型上都有提升，但提升幅度并不一样，能力弱一些的模型未必能充分利用仪表盘。

对比方法

论文对比的基线比较全，可以大致分成下面几类：

类别 方法 做法 问题
规则删除 ReAct、Tool-result Clearing、Fixed Stale Masking 追加历史，超限后截断或屏蔽旧工具结果 简单，但删掉后通常无法恢复
模型摘要 SLIM、Active Context Compression、Skeleton Compression 把旧轨迹改写为摘要或骨架 URL、ID、表格行等细节容易丢

Token 估计误差实验

论文还做了一个比较关键的实验：去掉仪表盘，让模型自己估计当前总长度、块大小和两个块谁更大。结果误差明显，说明模型不能只靠“感觉”判断上下文用了多少 Token。这个实验比单纯比较最终成功率更能说明仪表盘为什么有用。

⭐Self-GC: Self-Governing Context for Long-Horizon LLM Agents

小红书 2026.7.1，未开源。

这篇论文似乎已经覆盖了之前想过的方向，即在前缀命中的成本限制下寻找更合适的上下文压缩策略。

痛点

目前的系统主要依赖两类方式：一类是在 Agent 运行过程中使用启发式策略，例如按时间顺序删除旧内容、屏蔽工具输出；另一类是在上下文接近长度限制时，让模型对已有上下文做一次最终自我总结。启发式方法虽然成本低，但无法判断某段内容未来是否仍然存在依赖；摘要虽然能够保留整体叙事状态，却经常丢失精确证据、定位信息以及之后仍需要编辑的具体内容。

概述

Self-GC 将用户轮次、工具执行片段以及技能状态转换为带索引的上下文对象；让一个独立的旁路规划器决定哪些对象应该进行 fold、mask 或 prune；同时由 Agent harness 负责保证这些操作具有可恢复的旁路存储、安全的提交边界，以及对 prefix cache 友好的提交策略。

Pipeline

方法图

图从左上看到左下，再看到右边。

Context Engine 位于对话历史和下一次输入之间，Agent loop 不做变动。系统先把 context 构造成 Context Object，再复制一份给独立运行的 Planner（应该是另一个大模型）。Planner 针对不同对象选择不同操作，Rehearse Projection 负责安全检查。计划不会立即提交，而是先进入延迟提交；只有压缩后的 Token 收益高于前缀缓存损失时才执行。LLM 一直看到的是 Active View。

补充：

  1. 完整上下文存放在 Full Transcript，给模型看的是 Active View，支持恢复。
  2. Planner 只生成计划。Fold、Mask 和 Prune 是固定操作，Planner 类似于填写参数，最后由 Harness 具体执行。另外，这里的 Mask 会保留首尾各 10%。

提交时机

论文考虑了前缀缓存，但这部分写得比较粗略。\(N_{future}\) 的估计方式没有说清楚；论文根据经验认为，预计压缩比例超过 30% 时提交比较有效。

2.2 重写式压缩

这类方法用摘要、折叠结果或精简文本替换原始轨迹。不同论文采用的训练方式和触发条件不同，但都在把已有轨迹重写成更短的工作状态。

⭐ACON: Optimizing Context Compression for Long-horizon LLM Agents

arXiv 2025；发表于 ICLR 2026 Lifelong Agent workshop

现有工作的痛点

  1. 对话摘要和静态文档压缩不一定能保住 Agent 执行中的前置条件、状态变化和精确变量。
  2. FIFO、滑动窗口等固定规则容易删掉动态变量、鉴权信息或分页游标。
  3. 联合训练 Agent 和压缩策略需要访问权重，多步 RL rollout 的成本也高，不适合直接套在闭源 API 上。

核心思想与 Pipeline

一句话概括：先找“原始上下文能成功、压缩后失败”的轨迹对，让强模型分析到底漏了什么，再改写压缩规则；最后把压缩器蒸馏到小模型。

实验设置

  • 基准：AppWorld、OfficeBench 和 Multi-objective QA。原文这里曾列入 WebVoyager，但 ACON 的论文和官方代码没有把它作为实验基准。
  • 指标：任务成功率、交互步数和峰值 Token。论文报告峰值 Token 减少约 26%–54%，但压缩本身会增加额外调用，不能只看上下文长度。

MemoBrain: Executive Memory as an Agentic Brain for Reasoning

Findings of ACL 2026

MemoBrain 把推理步骤整理成带依赖关系的记忆。主 Agent 继续执行，旁路的 MemoBrain 异步维护这些状态，在上下文接近预算时删掉无效步骤、折叠已经完成的子轨迹，再重建一份较短的工作上下文。

这里需要单独注意：论文主要研究任务效果和记忆组织，不是 prefix cache。它会重写工作上下文，因此在按前缀计费的 API 上可能造成 cache miss，这部分成本不能直接忽略。

整体架构与工作流程

主 Agent 产生 Episode，MemoBrain 将其整理成 Thought 单元，并记录上下文来源、决策和产出。达到预算后主要做三件事：

  1. 根据依赖关系找出当前仍然有效的状态；
  2. 把已经完成的连续子任务折叠成摘要；
  3. 删掉失败或已经被后续结论替代的探索。

之后再把保留下来的 Thought 组装回主 Agent 的工作上下文。

实验评测

  • GAIA：复杂多步工具调用；
  • WebWalkerQA：跨多层网页的信息检索；
  • BrowseComp-Plus：需要多轮搜索和证据整合的任务。

这篇更值得关注的是“依赖感知的执行中记忆”，不是单纯把旧内容重新总结一遍。

⭐Context as a Tool: Context Management for Long-Horizon SWE-Agents

这篇和Self-Compacting很像但做的更好，同时也收录在ACL Findings

痛点

同 Self-Compacting。

创新点

主要思路也与 Self-Compacting 相近，但它不是让模型通过 Prompt 压缩，而是通过训练让模型学会自己压缩。

方法

运行时：上下文分为 \((Q, M^t, I^k)\)。Q 是不允许压缩的固定信息，例如 System Prompt、用户最初任务和核心任务目标；M 是中间积累的大量内容，也是主要压缩对象；I 是最近 \(k\) 轮交互历史，不压缩。

训练：

  1. 先生成正常运行的轨迹
  2. 离线手动寻找应该压缩的位置，插入标记
  3. 分成\(（Q,M^{t},I^{k}）\)的格式，交给Summarizer进行压缩（与运行时的模型采用同一系列的基座模型）
  4. 再过滤一些质量差的（没解决任务；进入不可恢复错误状态；context 调用过于频繁；压缩没有明显信息收益；摘要产生严重语义漂移；内部状态不一致。）

实验结果

Token没有节约多少，也是成功率略上升

主要结果 1：主要关注最后三行，Pass@1 有提升。

主要结果 2：作者说明，在提高最大交互步数的情况下，该方法的提升更明显。这个结果感觉比主要结果 1 更重要，但 Token 节约仍然不多。

论文观察到比较典型的触发场景有：

  1. 一个子任务已经完成；
  2. 上下文已经明显增长；
  3. 多次失败之后找到新的方向；
  4. 后续推理更需要简洁总结，而不是原始日志

AgentDiet: Reducing Cost of LLM Agents with Trajectory Reduction

AgentDiet 把轨迹中的浪费分成无用（Useless）、冗余（Redundant）和过期（Expired）三类，再用旁路反思模型压缩较早的步骤。它只修改一个滑动窗口，能够保住更早的稳定前缀，不完全是硬规则删除。

AgentFold: Long-Horizon Web Agents with Proactive Context Management

AgentFold 针对长程 Web Agent，让模型学习在每一步选择不同粒度的 folding：既可以压缩局部细节，也可以折叠完整子任务。它使用学习得到的 folding policy，不是固定规则。

共同问题：两者都会修改轨迹文本。AgentDiet 有意限制重写窗口，AgentFold 更关注任务效果；如果用于按 prefix cache 计费的 API，还需要单独核算重写造成的 cache miss。

Self-Compacting Language Model Agents

感觉这篇质量不太好（从方法和实验结果两个角度说），但这篇的 idea 可能值得参考或者避雷。按内容压缩的效果可能一般。

痛点：作者认为当前主流的两类规则（快到 content limit 才压缩，或者每隔固定 Token/Turn 压缩一次）只关注 context length，不够关注推理逻辑。

概述：作者让模型在子任务完成或推理完成时自适应压缩上下文。流程可以概述为：正常推理/搜索 → 检查当前工作是否已形成完整结果 → 若尚未完成则保留全部上下文 → 若已完成则提取关键事实并删除旧过程 → 基于压缩后的信息继续执行。

创新点：把上下文压缩从长度驱动改为 reasoning-state 驱动。

方法：没有训练，只在 Harness 层实现，从头到尾没有第二个模型。

作者设置了固定超参数 \(N\)，每隔 \(N\) 轮判断一次是否压缩。系统会在当前对话中追加一段内容，让模型回答几个作者设计的结构化问题。每个场景还要单独设计，泛化性一般。数学和搜索场景使用的问题也不一样。如果判断需要压缩，模型会把当前轨迹总结成一段更短的自然语言状态，再用 summary 直接替换原来的长轨迹，没有继续细分其中的文本。

实验：主要结果如下。论文对比的基线较少；与固定间隔压缩（30% Fixed-interval）相比，多数情况下 cost 甚至更高，只能说准确率也提高了一点。

2.3 缓存友好的上下文执行

上下文变短不一定就更便宜。如果每次都重写中间历史，原来的稳定前缀会被打断，后续请求需要重新 prefill。Token 数量、cache hit 和实际价格应该一起算。

⭐TokenPilot: Cache-Efficient Context Management for LLM Agents

TokenPilot 的重点不是把文本压到最短，而是在删内容时尽量保住 prefix cache。它分成两部分：输入内容第一次进入上下文时先做规则清洗；运行过程中再根据任务状态批量逐出已经失效的片段。

整体流程

目标

目标同时考虑保留下来的信息价值和实际 serving 成本，其中 cache hit Token 的价格低于 cache miss Token：

实验设置

  • PinchBench：11 类、123 个代码和办公任务；
  • Claw-Eval General：11 类、161 个沙盒多步任务；
  • Isolated Mode：每个任务结束后重置上下文；
  • Continuous Mode：同类任务放在一个长会话中连续执行。

主 Agent 使用 GPT-5.4-mini，状态评估器是 Qwen3.5-35B-A3B。论文采用的价格是： \[p_{\text{hit}}=\$0.075/\text{M},\quad p_{\text{miss}}=\$0.75/\text{M},\quad p_{\text{out}}=\$4.50/\text{M}\]

PinchBench：MemoBrain 的成本已经比较接近 TokenPilot；TokenPilot 在连续模式下仍保持了更低的总成本。

Claw-Eval：Keep-Last-N 是成本上最接近的基线之一。

连续会话中的 Token 变化：会议分析这类任务边界比较明确，上一段任务结束后就能逐出大部分旧内容，因此上下文长度较稳定。

几个比较有用的实验结论

  1. 动态字段要稳定：时间、绝对路径等字段如果每轮都变，会让前缀从很早的位置开始失效。

  2. 原文恢复不能省：禁用外部工件恢复后，Agent 会重复读文件、重复调用工具，总成本反而上升。

  3. 不能每轮都删：实验中 \(B=3\) 的综合结果最好。\(B=1\) 会频繁改写上下文，cache miss 增加；完全不逐出又会让历史持续增长。论文使用的等效输入成本是： \[\text{Equal}_{\text{input}} = C_{\text{miss}} + \alpha \cdot C_{\text{hit}} \quad (\text{如 } \alpha=0.1)\]

  4. 任务结束不等于信息立刻没用：如果刚完成任务就删掉全部相关内容，后续任务可能重新读同一个文件。Residual Utility 的作用就是给这些内容留一个缓冲期。

    图左：缺乏残余效用估计；图右：TokenPilot 正常缓冲机制

  5. 局限：状态评估器可能误判；方法依赖后端支持 prefix cache；主实验把同类任务放在一起，混合任务流中的复用机会会更少。论文补充实验仍有成本优势，但比同类任务连续运行时弱。

Leyline: KV Cache Directives for Agentic Inference

Leyline 从 serving 层解决“Agent 改了中间历史后，后面的 KV Cache 怎么继续用”这个问题。Agent 或上层策略只需要发出要替换的 span 和 replacement，底层再决定如何执行。

以删除第 2 轮工具输出为例：

  1. 用一个很短的 stub 替换原内容；
  2. 保留没有变化的前缀；
  3. 对后续缓存位置做 \(\delta\)-rotation 校正，避免把后面的内容全部重新 prefill。

这里有一个很重要的细节：原地 splice 保留了后续 KV，而这些 KV 是在看到原始内容时算出来的。因此它节省了 prefill，但不等于真正“忘掉”被删内容。如果要求语义遗忘，Leyline 仍需要走 re-prefill 模式。

目前闭式旋转主要在 MLA 架构上验证，GQA/MHA 还需要边界重计算等额外处理。这个方向很偏推理后端，商业闭源 API 也无法直接使用。

三、降低完整任务中的无效行动成本

这一部分关注 Agent 为完成任务执行了多少搜索、工具调用和重复尝试。上下文压缩可以作为其中的手段，但分类依据是它是否减少了任务中的无效行动。

3.1 复用已有探索结果

⭐RE-TRAC: REcursive TRAjectory Compression for Deep Search Agents

多轮深度搜索很容易在不同 rollout 中重复走相同的错误路径。RE-TRAC 不是每轮对话都做摘要，而是在一条完整搜索轨迹结束后，把证据、不确定项、失败方向和下一步计划压成结构化状态，再交给下一条轨迹继续搜索。

实验

  • 数据集包括 BrowseComp、BrowseComp-ZH、GAIA、XBench 和 HLE；
  • 对比单次运行、Best-of-N、多数投票和加权投票；
  • 除正确率外，还统计工具调用和 Token。论文观察到后续轮次的调用量和 Token 会下降，说明前一轮的结构化状态确实减少了一部分重复探索。

3.2 训练成本感知的行动策略

SlimSearcher: Training Efficiency-Aware Web Agents via Adaptive Reward Gating

SlimSearcher 在 SFT 阶段筛选正确且便宜的轨迹；在 RL 阶段先用正确性做门控，再比较同组样本的工具调用和 Token 成本，避免模型单纯为了变短而不搜索。它优化的是完整搜索过程中的行动策略，不是模型内部的 Token 或 Attention 剪枝。

3.3 继续、停止、恢复或升级

  • EET：研究 Agent 是否应该提前停止，避免在低收益状态下继续消耗预算。
  • CodeRescue：研究失败后应该继续廉价恢复，还是升级到更强模型。

这两篇目前只在发展历程中简要记录。如果之后补充正文，可以放在这里。

四、降低单次模型调用的推理成本

这部分讨论一次模型调用内部生成了多少推理内容、保留了多少中间状态，以及每个 Token 使用了多大的模型。

4.1 缩短显式推理链

Making Slow Thinking Faster

Making Slow Thinking Faster 提出 Step Entropy，用每个推理步骤的信息量判断它是否冗余。训练分为 SFT 和 GRPO 两阶段，让模型在低熵步骤处输出 [SKIP]，少写一些重复验证。这篇是 ICLR 2026。

TokenSkip: Controllable Chain-of-Thought Compression in LLMs

TokenSkip 构造不同压缩率的 CoT 数据，再微调目标模型，使它能按给定比例生成更短的推理链。原文这里写成“小模型逐 Token 打分”不准确。

CRISP: Compressing Redundancy in Chain-of-Thought via Intrinsic Saliency Pruning

CRISP 利用模型在 </think> 位置的注意力作为显著性信号，判断哪些推理步骤更重要，再据此做细粒度压缩。它不是在每个解码步里动态删 Token。

4.2 提前分配推理预算

SelfBudgeter: Adaptive Token Allocation for Efficient LLM Reasoning

最早于 2025.5，最后更新于 2026.4；ACL 2026 Findings；53 引用。

痛点

推理模型容易 overthinking。当前已有三类方法：Prompt 方法通过“简短回答”“最多 N Token”等指令控制长度，但控制不精确；训练型方法通过 SFT 或长度奖励让模型缩短推理，但往往不能严格满足指定长度；Router 方法用额外分类器决定调用哪种模型或推理路径，因此增加了额外计算模块。

Insight

  1. 虽然 reasoning model 会 overthink，但总体上问题越难，模型自然生成的推理越长，说明模型内部已经具有某种问题难度 → 所需计算量的判断能力。
  2. 已有研究说明模型可以学习 Token Budget → 对应长度输出。

作者首先训练模型，使其能够根据输入问题自行估计完成推理所需的 Token Budget；随后引入 budget-guided GRPO 进行强化学习，在尽可能缩短输出的同时保持准确率。

方法

训练分为三个阶段：

  1. 用原始模型生成数据，记录 \((Q,A,C,L)\)，分别对应问题、回答、是否正确和实际 Token 数。
  2. 进行冷启动，让模型先学会输出 Budget。作者认为直接进行 RL 时，模型很难同时学会“输出新格式 + 预测预算 + 遵守预算 + 正确回答 + 缩短推理”，因此先用 SFT 学习行为模式。
  3. 采用 GRPO 进行 RL 训练。模型针对问题生成 <budget>b</budget> <solution>...</solution>，关注模型预测预算 \(b\)、实际生成长度 \(\ell\) 和答案正确性 \(C\)，用 reward 同时优化正确性、Budget 大小和 Budget 遵守程度。

如果用户没有指定预算，模型会先预测完成任务需要的 Token 数。

Reward 模块

  • Format：格式是否正确；
  • Budget Penalty：推动模型压低预算；
  • PreB：让实际长度与 Budget 对齐；
  • Correctness Reward：防止模型为了节省 Token 而随意作答。

Reward 详情见论文。

4.3 压缩为潜在表示

LightThinker: Thinking Step-by-Step Compression

EMNLP 2025

LightThinker 训练模型把已经完成的思考步骤压到少量 Cache Tokens 中，后续推理不再访问原始步骤。它节省的是运行时保留的上下文和 KV Cache，不只是让最终输出看起来更短。

两个核心问题：何时压缩？如何压缩？

  1. 何时压缩：先把 CoT 划分成思考步骤，并插入压缩触发 Token、Cache Token 和 Output Token，让模型学习在步骤边界压缩。
  2. 注意力掩码控制：
    • 压缩 \(S_i\) 时，Cache Token 可以看到问题、之前的 Cache Tokens 和当前步骤；
    • 生成 \(S_{i+1}\) 时，Attention Mask 屏蔽原始的 \(S_i\)，只保留问题和压缩后的表示。

闭环流程

  1. 生成 Thought 1；
  2. 将 Thought 1 压到 CT1；
  3. 后续 Attention 不再访问 Thought 1；
  4. 基于问题和 CT1 生成 Thought 2，之后重复这个过程。

4.4 大小模型路由

⭐PyroDash: Cost-Efficient Token-Level Small-Large Language Model Collaborative Inference

参考自机器之心的：当小模型学会了何时求助

目标：减少 Token 成本。

核心方法

在需要时调用大模型，其余时候由小模型完成。最近两年的路由方法开始从“任务开始前根据难度选择模型”转向“在生成过程中继续决策”。PyroDash 相比逐 Token 评估路由器的优势在于：决策完全内化在小模型中，不需要外挂路由器；交接单向且至多一次；只使用标准文本续写接口，不访问大模型内部。

生成过程中决策的例子：CITER 训练一个成本感知的 MLP 路由器，逐 Token 决定由谁生成；Co-LLM 把交替解码学成隐式模型选择；RelayLLM 让小模型主动发出指令，请求大模型生成一段有界长度的内容，再把控制权交还小模型；GlimpRouter 免训练，用每个推理步首个 Token 的熵作为不确定性信号，必要时反复调用大模型。

PyroDash 是一种成本感知、Token 级的大小模型协同推理范式。整套系统有三个部件：一个可训练的小模型、一个保持冻结的大模型，以及负责执行交接的协同引擎（Collaborate Engine，简称 CE）。

其工作方式可以概括为：小模型优先、至多一次、单向不返回。

请求进入后，CE 先把它连同固定的系统提示交给小模型。小模型以流式方式开始生成：

  • 如果它能独立完成，结果直接返回用户，全程不调用大模型。
  • 如果它在某一步判断自己无法继续，就输出专属控制 Token（论文记作 \(\tau_{off}\)）。CE 检测到这个信号后停止小模型解码，移除控制 Token，再将原始问题和已有的部分推理轨迹一次性交给冻结的大模型，由大模型继续生成答案。控制权不再返回小模型，一个请求最多调用一次大模型 API。

具体实现

  1. 构建 EasyHard-24K 数据集。
  2. 先用基础小模型运行每条样本。答对的进入 easy 子集；答错但能够重构出正确推理轨迹的进入 hard 子集。【那每个新的小模型都要这样？泛化性疑似一般。】
  3. 对 hard 样本，用大模型重构一条能导向正确答案的简洁思维链，再在正确轨迹中动态插入一到四个候选交接位置。
  4. 数据扩展成两种提示条件：一份不含协同提示，轨迹中也没有 \(\tau_{off}\)，用于保留小模型原有的独立推理行为；另一份加入协同提示，其中 easy 样本的目标仍不含 \(\tau_{off}\)，避免模型无必要地调用大模型。
  5. 训练分为三个阶段。第三阶段使用成本感知的 GRPO 进行策略对齐，训练时执行与推理时相同的单向交接路径。详情见链接。

五、归档方向：Skill 优化与长期管理

暂存结论：目前优先做整体 Agent Token Efficiency，Skill 相关内容先放在这里。

  1. Skill 文本压缩：例如从 SkillReducer 继续做 SkillZip，减少说明文档和 Prompt 本身的长度。
  2. Skill 库的长期管理：任务积累后，单个 Skill 和整个 Skill 库都会越来越大，检索、选择也会变贵。
    • 之前想过信用分：调用成功就加分，失败就扣分。但这里最难的是归因，任务失败不一定真的是 Skill 的问题，可能还需要一个独立模型判断。
    • SkillClaw 的思路是把维护过程交给异步的独立 LLM，和主 Agent 解耦。
  3. 过拟合和表达形式：
    • Skill-on-the-fly 更像临时合成，不完全是长期自进化；离线测试集能检查过拟合，但在线验证成本又比较高。
    • 表达形式可能从文本走向代码或参数。文本最容易解释和修改；代码适应性有限；参数虽然紧凑，但更黑盒，目前看性价比不高。

How Do AI Agents Spend Your Money? Analyzing and Predicting Token Consumption in Agentic Coding Tasks

2026.4 机构有密西根大学、斯坦福、all hands AI等 看着内容也比较扎实

这篇论文是实验为主

痛点：

论文实验显示 Agentic Coding 平均 token 消耗比单轮代码推理高约 3500×，比多轮代码聊天高约 1200×。因为每轮使用工具以及分析都是把前面的上下文一起送入大模型，输入tokens消耗相比传统LLM多很多。

实验结论：

64%的轮次都在Explore和Fix阶段，这个阶段有大量重复的动作。

同时作者也从cache与否，input与否对每轮的cost进行了分析

cost高点主要是因为：查看新文件；pytest 输出大量结果；创建 script；引入新的 repository 内容。

六、个人科研思考

1. 动态决定压缩时机和压缩程度

沿着 TokenPilot 继续做，重点还是压缩收益和 prefix cache 损失之间的 trade-off。

  • TokenPilot 固定每 3 轮检查一次，输入清洗也有不少固定截断规则。复杂任务里可能删早了，简单任务里又可能拖太久。
  • 能否用很轻量的策略，或者模型内部的不确定性、注意力熵，动态决定什么时候压缩、压多少？
  • 也可以借鉴 VISTA 的仪表盘，让主 Agent 看到预算和上下文状态后主动请求压缩。但要避免它只会看长度，不会判断后续依赖。

汇报

大致按照“背景>任务>挑战>方法>结果>分析>下一步计划”来组织材料，不一定全要有，根据实际内容适当组织即可，保证PPT质量

背景：上下文压缩

任务/指标：

  1. 提高任务通过率
  2. 任务通过率不变或者更高的情况下降低tokens消耗

本来的具体想法：在前缀命中的成本限制下，思考一个更优解的上下文压缩策略。这已经被Self-GC做了。

另外关于压缩时机（TokenPilot是固定Batch=3）以及如何压缩的更小也都有工作在做（见下）

  • 关于时机：以前是硬性规则，现在倾向是让模型自己决定。【可能是因为觉得现在模型性能足够了】
  • 关于谁来压缩：大概有三类，硬性规则(Self-GC)，模型自主压缩(Context as a Tool)，旁路模型压缩(AgentFold)。现在比较倾向让模型自己压缩
  • 关于怎么压缩到最小的同时不影响成功率：也有不少工作在平衡，主要是通过训练的方法，ACON，BudgetMem，SelfBudgeter（不是压缩但有相似的思路，通过训练让模型自己给出对任务预计耗费的token并控制token输出）。

Self-GC: Self-Governing Context for Long-Horizon LLM Agents：Self-GC 将用户轮次、工具执行片段以及技能状态转换为带索引的上下文对象；让一个独立的旁路规划器决定哪些对象应该进行 fold、mask 或 prune；同时由 Agent harness 负责保证这些操作具有可恢复的旁路存储、安全的提交边界，以及对 prefix cache 友好的提交策略。

Context as a Tool: Context Management for Long-Horizon SWE-Agents：通过训练让模型学会自己压缩

Self-Compacting Language Model Agents：通过Prompt和系统设计让模型自己压缩（但质量一般），感觉纯Prompt这个方向需要避雷，结合其他来看，可能还是需要训练才能让模型更擅长自己管理上下文。

AgentDiet: Reducing Cost of LLM Agents with Trajectory Reduction：用旁路模型来压缩

ACON: Optimizing Context Compression for Long-horizon LLM Agents：通过训练和蒸馏让旁路模型学会怎么压缩。具体来说构造“原始上下文能成功、压缩后失败”的轨迹对，让强模型分析到底漏了什么，再改写压缩规则；最后把压缩器蒸馏到小模型。

Codex 的实验性上下文管理：工业界的举动，告诉模型压缩时机，让模型自己切换上下文（不压缩，只切换，需要的时候再换回来，但具体怎么实现的还没看）

VISTA:论文认为成熟模型可能已经有一定的上下文管理能力，只是它看不到每块内容用了多少 Token、多久没访问等状态。作者因此设计了 VISTA，把这些信息做成一个“状态仪表盘”，不训练模型，只增加接口。

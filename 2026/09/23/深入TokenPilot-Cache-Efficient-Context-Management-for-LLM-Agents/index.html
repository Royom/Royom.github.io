TokenPilot: Cache-Efficient Context Management for LLM Agents

剪裁/压缩会导致cache不连续，产生额外的成本

一个显而易见需要平衡的地方是：一方面需要减少上下文页面的长度，另一方面又需要提高硬件缓存的效率。

TokenPilot 的重点不是把文本压到最短，而是在删内容时尽量保住 prefix cache。它分成两部分：输入内容第一次进入上下文时先做规则清洗（对应全局摄入感知压缩框架）；运行过程中再根据任务状态批量逐出已经失效的片段（对应生命周期感知逐出）。

整体流程

前缀稳定化：主要是在跨任务共享KVcache时

清洗：重复读取去重、工具结果裁剪、HTML清晰、超长输出截断。

目标

同时考虑保留下来的信息价值和实际 serving 成本，其中 cache hit Token 的价格低于 cache miss Token：

实验设置

  • PinchBench：11 类、123 个代码和办公任务；
  • Claw-Eval General：11 类、161 个沙盒多步任务；
  • Isolated Mode：每个任务结束后重置上下文；
  • Continuous Mode：同类任务放在一个长会话中连续执行。

主 Agent 使用 GPT-5.4-mini，状态评估器是 Qwen3.5-35B-A3B。论文采用的价格是： \[p_{\text{hit}}=\$0.075/\text{M},\quad p_{\text{miss}}=\$0.75/\text{M},\quad p_{\text{out}}=\$4.50/\text{M}\]

PinchBench：MemoBrain 的成本已经比较接近 TokenPilot；TokenPilot 在连续模式下仍保持了更低的总成本。

Claw-Eval：Keep-Last-N 是成本上最接近的基线之一。

连续会话中的 Token 变化：会议分析这类任务边界比较明确，上一段任务结束后就能逐出大部分旧内容，因此上下文长度较稳定。

几个比较有用的实验结论

  1. 动态字段要稳定：时间、绝对路径等字段如果每轮都变，会让前缀从很早的位置开始失效。

  2. 原文恢复不能省：禁用外部工件恢复后，Agent 会重复读文件、重复调用工具，总成本反而上升。

  3. 不能每轮都删：实验中 \(B=3\) 的综合结果最好。\(B=1\) 会频繁改写上下文，cache miss 增加；完全不逐出又会让历史持续增长。论文使用的等效输入成本是： \[\text{Equal}_{\text{input}} = C_{\text{miss}} + \alpha \cdot C_{\text{hit}} \quad (\text{如 } \alpha=0.1)\]

  4. 任务结束不等于信息立刻没用：如果刚完成任务就删掉全部相关内容，后续任务可能重新读同一个文件。Residual Utility 的作用就是给这些内容留一个缓冲期。

    图左：缺乏残余效用估计；图右：TokenPilot 正常缓冲机制

  5. 局限：状态评估器可能误判；方法依赖后端支持 prefix cache；主实验把同类任务放在一起，混合任务流中的复用机会会更少。论文补充实验仍有成本优势，但比同类任务连续运行时弱。

CADOC: Cache-Aware Dynamic Object Context for Long-Horizon Agents

2026.9.29 上交团队 通讯作者是数院教授 arxiv预印

重要论文，和研究方向高度契合，之前看的TokenPilot和Self-GC都有在文中被引用

这篇论文最重要的洞见是：历史对象可以先获得替换资格，但延迟到合适时机再一起替换；批量提交能够分摊前缀缓存重建成本，而等待的代价可以用已经发生的重复输入来累计，无须预测未来还会调用多少次模型。

下面围绕三个问题展开：这个代价怎样算，为什么得到论文的阈值规则，以及实验究竟证明了多强的优势。

论文复现

  1. 采用的配置：2026.9.26最新的Lightrsi和Openclaw。论文作者回复到采用的是2026.3.12的Openclaw
  2. 出现的问题：
    1. 一方面本身就跑不通，这里面有部分是OpenClaw更新版本改了一些结构和字段的原因，但改了这些后还有其他的和OpenClaw之间的交互问题。以及从它仓库最新版设的字段来看它目前用的也是比较新版的OpenClaw，所以我暂时是在新版本上进行的修改尝试复现（尝试了老版本的组合但还存在下面另一方面问题）。【发了邮件给作者但暂未得到答复】
    2. 另一方面，除了插入到OpenClaw的适配问题外，它开源的仓库也有一些内容没按论文的来设计，比如前缀稳定化这里写了部分的处理的方式但又没在代码里真的使用
  3. 需要问原作者的问题
    1. lightrsi有把论文里的TokenPilot都整合进来吗？我看框架里面有一些东西是没有实现的，比如压缩门槛我看有设置但没实际用于筛选压缩对象，格式、路径、行号清理也只有设置没有应用
    2. 论文实验的主模型使用的是哪家 API 服务？我测试过程中发现API服务提供商会有一些影响，我现在复现实验中有部分任务tokens的降幅比较明显但cost收益距离论文给出的数据还有一定距离。

最后采用2026.5.2的Lightrsi+2026.3.12的Openclaw

探索实验

  1. 实验内容：在Pinchbench数据集的不同任务类型上跑Vanilla和TokenPilot，以isolated模式为主 目的：探索是否存在有一定普适性的问题 结果：continuous仍然较短，没找到认为有价值的问题。有些题目cost是更高但没有共同的原因。
  2. 实验内容：拆分组件看效果 目的：看看不同组件的贡献 结果：组件都对实验结果有贡献 有一些结论：完整工具观察能提升一点分数但cost也会提升不少，Openclaw本身有工具裁剪的。内部估计器的费用实际上也不少。
  3. 实验内容：参照 CADOC，在固定轨迹上比较立即压缩、固定批量和动态提交。 目的：判断只优化编辑时机，能否明显降低缓存重建费用。 结果：简单修改提交门槛没有稳定优势，部分省费来自最终少提交了对象；已有轨迹上的额外调度空间有限。 特别标注：离线代理成本不能等同于线上费用与质量收益。
  4. 实验内容：受到CADOC将一个数据集的题组成一个超长任务对话的启发，我认为目前的数据集可能一个上下文中任务的数量不够，所以从会议记录分析和日志记录里挑选了20道题(14+6)组成mixed20，在固定的 mixed20 连续任务链上，对比完整 TokenPilot、C2（当前任务观察保护＋reasoning.context=current_turn）和 C3（C2＋历史报告归档成 Card 的形式）。 目的：看看在更长上下文情况下模型压缩的表现，比较任务质量与完整任务链成本的取舍。 结果：TokenPilot／C2／C3 的混合均分分别为 0.8070／0.9083／0.8133，已知链费用分别为 0.7562／0.2791／0.1667 元。C2 在本链中取舍最好；C3 相对 C2 的 tokens、费用均下降约40%，但质量明显下降，并出现旧任务错位。TokenPilot在长上下文的情况下出现表现不良。
  5. 实验内容：进一步转向CADOC所涉及的数据集 Terminal-Bench 2.1，开展分类 continuous 的 C2／完整 TokenPilot 对照。 目的：用公开任务和官方验证器检验已有现象，减少自选题与评分噪声的影响。 结果： 特别标注：我采用了在10个分类里每个题选5道组成的超长任务链，而不是像CADOC把89道题都拼在一起（成本原因）

mixed20 连续任务链：Off、C0—C3 与 TokenPilot 对比

主模型、外部评分器均使用 Chickener GPT‑6‑Luna；C1 和 TokenPilot 的内部估计器也使用同一模型。任务链包含主模型与内部估计器，不包含外部评分。

条件说明

  • Off：关闭 TokenPilot，使用 OpenClaw 原生上下文处理。
  • C0：保护当前任务观察，保留全部 reasoning，关闭估计器与任务淘汰。
  • C1：保留全部 reasoning，启用 Luna 估计器、任务淘汰，并对齐生命周期提示。
  • C2：在 C0 基础上使用 current_turn。
  • C3：在 C2 基础上，将历史生成报告正文归档为 Card。
  • TokenPilot：完整兼容版，启用原估计器提示、工具观察压缩和任务淘汰，主模型使用 current_turn，没有 C2 的当前任务观察保护。该版本不是已确认的论文实验 commit。

主要观察

  • C2 相对 C0：混合均分提高约0.170，四道严重旧任务错答得到缓解，但费用增加约27%。
  • C3 相对 C2：tokens、费用均下降约40%，混合均分下降约0.095，并再次出现旧目标错位。缓存率仅提高0.77个百分点，降本主要来自携带内容减少。
  • TokenPilot 相对 C2：已知链费用约为2.71倍，主模型调用为423次对148次，混合均分低约0.101。估计器仅占 TokenPilot 已知链费用的2.48%，主要开销在主模型执行链。
  • 当前判断：C2 在本次观察中具有较好的质量—成本取舍；C3 尚未守住质量；完整 TokenPilot 未显示整体优势。

想法

  1. 压缩的机理或许有用。让模型来压缩，会把之前的上下文都变成摘要的形式，同时再之前的摘要也会被压缩。优先保护用户原文，其余的无论是工具调用还是模型回复都要压缩。

需要给AI讲清楚的规则

  1. 计算费用的时候按官方定价而不是中转站定价，所以在计算费用时应当把费用再除以中转站的折扣，这样才能得到一个统一的价格。
  2. 除了在复现原论文结果时要采用与原论文相同的Gpt-5.4-mini模型和Qwen模型，除非我额外指定，不然后续在我目前的实践中都采用Gpt-6-luna作为主要模型以及内部评估器模型和打分模型。因为原来的Gpt-5.4-mini模型和Qwen模型都比现在的模型更贵，都替换为采用现在的模型会更合适。
  3. 我关注的主要是模型在执行过程中是否存在某种具有一定普遍性的问题，但为了保证执行结果正确，我也要确保方法之外的其余系统是否正常，模型可以执行出错，但我要排除因为网络、TP本身系统外的系统错误等等方面的原因。

询问导师的问题

  1. 对于模型在数据集上有时候意外的错误，该怎么处理。比如T143问题模型本来该恢复相关的内容，但就好像没找到数据key在哪一样一直寻找同时以枚举的方式尝试找到数据key，产生大量cost。
  2. 模型更换后导致的结果上的不同怎么看待？比如gpt-5.4-mini时Tokenpilot方法优于Vanilla，但换成Gpt-6-luna的时候就劣于Vanilla
  3. 我在实验过程中发现，论文在Claw-Eval数据集的长任务链模式下的实验统计有很严重的问题，简要地说结果的话，相当于作者在论文里说自己方法的开销是100，Vanilla的开销是800，但是我审查下来Vanilla的真实开销是60，也就说原生甚至比Tokenpilot的cost还低40%，核心原因是Tokenpilot方法的前缀缓存率相比Vanilla在这个数据集测试中低了30%。我联系论文第一作者核对了，确实存在这个问题，论文作者解释说实验是四名提前进组的本科生分别做的，他自己没做详细地审查。然后我又审查了一下其他的实验数据，发现除了Vanilla外其余的作为基线比较的方法有至少5个也存在同样的统计问题。综上所述，我觉得应该很难再以它为基准继续做了，因为它实验部分的篓子实在有点多。

Skill的结构（if使用渐进式披露）

LangChain 还提到过一个 model-harness 耦合现象。现在很多 Agent 产品，比如 Claude Code、Codex，模型和 Harness 是一起被调优出来的，这会带来一种过拟合：模型习惯了某套工具逻辑，换一个 Harness 后表现可能变差。他们在 Terminal Bench 2.0 排行榜里观察到，Opus 在 Claude Code 的 Harness 下得分，远低于它在其他 Harness 中的得分。

[一文读懂 Harness Engineering：从 14 篇工程文章中，寻找那个让 AI 不再离经叛道的壳](https://www.superlinear.academy/c/share-your-insights/harness-engineering-14-ai)：这篇对历史梳理的比较仔细，涵盖了Agent进化过程中增加的组件

  1. 随着模型的升级，Harness的架构也会发生改变，Harness的组件是为了解决模型做不到的某件事，但模型的进步让它能自己完成这件事后就可以去掉这个Harness的组件了
  2. 而 Cursor 也从另一个角度证明了这一点。还是第二章里那个几百个 Agent 集体摸鱼的项目——同时跑七天，写一个浏览器。在反复调试的过程中，他们发现影响系统行为最大的因素是 prompt（即，你怎么用自然语言跟 Agent 说话），其次是 harness 结构，最后才是模型本身。但这个排序有前提。Cursor 得出结论时，harness 已经是 planner-worker-judge 三层架构，经过了多轮迭代。Prompt 站在 harness 的肩膀上，才有了那个影响力。没有那层架构，再好的 prompt 也只是对着一群互相踩踏的 Agent 喊话。这个排序反映的是边际影响力，不是基础重要性。
  3. 前面三层壳解决的都是同一个问题，怎么让 Agent 把长程任务做好。记忆是为了不忘事，并发是为了干大活，验证是为了不糊弄。它们都是执行长程任务的必需品。

实际中的Skill问题：

  1. Skill投毒 涉及到使用一种Unicode隐藏字符的技术。大概的原理就是使用了一些在大部分编辑器下是不可见字符的Unicode编码。导致我们肉眼是看不到的，但是LLM是可以看见的。来藏一个带毒的步骤。MCP和SKILL类似，利用LLM无法正确区分数据与指令以及其对上下文输入的高度依赖性灯特性，攻击者通过在与模型交互的数据源中植入恶意指令，诱导模型执行非预期操作，甚至可进一步实现对AI Agent的行为劫持与权限滥用。不过目前的Harness（比如Codex）有对这个的防御，可能有对不可见字符的过滤、沙箱/权限拦截、模型/对齐层面的鲁棒性。
  2. 更具体的Skill投毒SKILL攻击策略的改进：
    • 通过明文指向隐藏的恶意指令，让指令不被忽略：不再依赖 tokenizer 能否保留不可见字符，而是让模型在语义层面主动‘去寻找’某段内容
    • 从单段指令注入转向语义混淆：让模型误判某段内容的“身份”（例如被误当作系统规则、执行规范、或工具调用准则），从而在对齐与过滤下仍获得更高权重。
    • 从隐藏指令转向内容投毒对抗：当直接触发高危动作很难时，攻击者可能退一步，把目标转为改变模型判断：让技能提供的“安全准则/命令白名单/最佳实践”本身带偏，从而在后续交互里促成更危险的操作。
    • 将攻击指令由单步骤拆分为多步骤：单个指令的意图过于明显时，攻击者可以将这个攻击指令的输入/输出拆分，改为多个步骤达到一个效果从而实现绕过。
  3. Agent Skills是什么：这一篇讲述了Skills的概念、设计方法。Skill有一些设计时应该注意的点，比如精简语言，用词准确之类的；还有比如渐进式披露、延迟加载这样的设计。自由度也是个问题。

A Survey on AI Agent Harness

一篇Harness的综述，Skill在里面在Layer2中有部分内容，从它归纳的角度或许能给我一些启发。 第四节Layer2：

Acquisition（获取）： 探讨智能体如何通过自我进化、多智能体交互或程序归纳来学习新技能 。

Selection and routing（选择与路由）： 当面对庞大的技能库时，智能体如何利用“检索-重排（retrieve-and-rerank）”等机制挑选最合适的技能 。

Optimization（优化）： 关注如何提升技能的执行效率（如减少 token 消耗）以及组合多个技能进行复杂推理 。

Evaluation（评估）： 测量技能增强后的单智能体架构极限及其在各种测试基准上的实际效果 。 第六节Layer4： 具体子节： Agent Injection, Persistent Threats, & Runtime Defenses

痛点与隐患： 论文指出，由于 Skill 具有可复用和易扩展的特性，它正在成为智能体系统的一个重要攻击面。扩展级注入攻击（Extension-level injections）会盯上这些技能插件，通过植入恶意技能、在代码中隐藏指令或利用脆弱的技能仓库，将原本一次性的提示词注入转化为持久化控制 。这要求底层框架必须对 Skill 实行严格的沙箱运行和动态权限管控。

SkillRouter: Skill Routing for LLM Agents at Scale

痛点：随着 LLM 智能体的发展，社区和企业内部积累的工具/技能库规模已达数万级别，在执行具体任务前，系统必须进行“技能路由”，从海量技能池中精准检索出匹配的技能，以避免将所有工具塞入上下文 。在拥有数万级、高度同质化（存在大量相似名称或泛化描述的干扰项）的真实技能生态中，仅靠元数据进行路由会导致严重的“特征缺失”，使模型无法区分功能相近的干扰项 。

作者经验发现：技能的完整文本（尤其是详细的主体代码或规范）包含了无法被简短描述替代的关键路由信号 。如果为检索和重排模型提供完整的全文访问权限，即使是小参数模型也能通过学习实现细节的细粒度差异，在高度重叠的候选集中实现极高的路由准确率

本文的工作：1.训练阶段：作者微调训练了两个0.6B的模型，第一个是双塔检索器，用于找到与用户请求最相关的skill【假负例过滤】；第二个模型用于对Skill的重要性进行排序，根据Query+第一个模型给出的Top20相关的Skill进行训练【列表级交叉熵】。2.推理阶段：先用query与第一个模型得到的skill向量【提前离线预计算】进行余弦相似度找到Top20相关的Skill，再将query与找到的skill拼接，然后交给第二个模型排序得到Top-k最好的Skill

AutoTool: Efficient Tool Selection for Large Language Model Agents

AutoTool 是一种轻量级框架，通过在重复性决策步骤中绕过大模型，显著降低了 LLM 智能体的高昂推理成本 。该方法基于历史执行轨迹构建了一个动态的“工具惯性图（TIG），以捕获工具调用的可预测顺序模式与参数级的数据流向 。在具体执行中，系统会优先结合历史调用频率与当前语境预测下一步工具，并利用前置步骤的输出自动进行参数填充 。只有当图谱预测分数过低或参数填充失败时，决策权才会回退给 LLM 进行标准推理，从而在保障任务完成率的同时，极大节省了 Token 开销和系统延迟 。 【这篇论文是指出了Tool工具调用倾向于遵循可预测的顺序模式。但Skill的调用可能不太一样，但或许仍然能通过某种算法将skill排个序？】 AI给出的idea：【架构改造： 不要再做静态的全局挂载。在 Harness 进入 LLM 推理层之前，增加一个轻量级的路由预处理层。利用类似论文中的综合惯性潜力得分（CIPS）——结合 \(\text{Score}_{freq}\)（历史状态转移概率）与 \(\text{Score}_{ctx}\)（当前任务语义相似度）——预测出当前步骤最可能需要的 Top-K 个 Skill。只将这 K 个 Skill 的 Schema 注入当次的 Prompt，这能从根源上将 Input Token 的消耗降低一个数量级。】 【架构改造： 将控制流与数据流解耦。在 Harness 中维护一个全局状态白板（Blackboard）或参数流向图。如果判断出下一个 Skill B 的必需参数，在历史记录中是由 Skill A 的输出生成的（例如 UUID、文本块），Harness 应直接在底层通过键值匹配自动完成填参并调用 。大模型不参与这部分数据的序列化生成，彻底消除数据搬运带来的 Token 冗余。】

SkillReducer: Optimizing LLM Agent Skills for Token Efficiency

基于Skills的二分结构，提出了一个两阶段的优化框架，第一阶段通过压缩冗余描述和生成缺失的路由描述via adversarial delta debugging优化路由层，第二阶段采用分类法驱动的分类器，调整程序切片原则，对文本进行结构性分割。结果是显著压缩，路由层平均压缩48%，主体层平均压缩39%，并且功能质量相比原来的还提升了2.8%。工作在多个模型和智能体框架中得到了验证。

极简特征提取（用排除法测试并删减路由描述的废话）

文本按类剥离（将长提示词拆分为核心指令、背景与示例）

构建按需工具（核心指令直给，背景示例变为可调用的文件）

任务试错回补（跑测试用例，缺什么信息就把什么信息塞回核心层）

阶段一：路由层优化 (Stage 1: Routing Layer Optimization)

预处理：描述生成与语义切分

  • 对于缺失或过短（\(\le 40\) tokens）的描述，利用LLM从技能正文中自动生成包含核心能力和触发条件的初始描述。
  • 将长描述切分为多个独立的语义子句（Semantic Clauses），避免句子级切分过粗或词汇级切分过细。

Phase 1: 模拟预言机与增量调试 (Simulated Oracle + DDMIN)

  1. TF-IDF 选出4个长得很像的技能，外加LLM生成的1个影子技能，组成“地狱难度”的候选池。
  2. DDMIN 将原始描述大卸八块，开始尝试各种删减组合。
  3. 模拟预言机 面对候选池，检验 DDMIN 每一次删减后的结果是否依然正确。 三者配合，最终榨干了技能描述中的所有水分，只留下极高信息密度的路由触发点。

Phase 2: 真实环境验证与选择性回补 (Real-Environment Validation)

  • 现实校验：模拟预言机速度快但容易“过度乐观”。因此，系统会将压缩后的描述放入真实的 Claude Code CLI 环境中测试触发率。
  • 贪心回补机制：如果真实触发率下降，系统会从被丢弃的子句中，贪心地挑出能最大程度提升触发率的子句并补回（Selective Restore），直到触发率恢复到原始水平。

阶段二：基于渐进式展现的正文重构 (Stage 2: Body Restructuring via Progressive Disclosure)

拆解与打标：把几千字的长文本逐段切开，甄别出哪些是必须遵守的“行动指令”，哪些是仅供参考的“补充资料”（比如名词解释、代码例子）。

精简与隔离：把“行动指令”缩写到极简，直接作为主要提示词喂给 AI；把“补充资料”精简去重后，移出主要提示词，存为一个个独立的文本文件。

配置按需触发：给那些存起来的独立文件写上一句简短的说明（例如：包含前端配置代码）。AI 在做任务时，只有它自己判断需要前端代码了，才会主动去读取那个文件。

跑测与纠错：让 AI 做几道测试题。如果发现 AI 因为没看到某一个被移走的“代码例子”而把题做错了，系统就会把那个例子从独立文件里拿出来，永久性地塞回主要提示词里，确保以后不再犯错。

思考：既然能压缩input，那输出是不是也可以压缩呢？压缩采用什么方法？指标采用什么？

这篇论文压缩历史轨迹符合导师提到的方向

概述：无需训练、黑盒兼容，通过将历史推理轨迹蒸馏成可复用的技能卡片，在推理时检索注入，实现了更少Token，更高准确率的反直觉突破

离线（Offline）：将模型解决历史问题时的长轨迹（包括成功路径和失败教训）蒸馏成结构化的技能卡片（Skill Card）

在线（Online）：面对新问题时，检索最相关的技能卡片注入Prompt，引导模型走"直达路径"

方法：

3.1 技能卡片的设计（Skill Card Schema）：五个字段，对于正确的解题轨迹，卡片提炼成功模式；对于错误轨迹，卡片提炼"反模式→修正策略"。

3.2 离线构建技能库：对源问题q，运行推理模型得到轨迹τ和结果y；c=eval(y,a)[a表示answer]，c的含义是结果是否正确。然后用更强的蒸馏模型将(q,τ,y,c)压缩为技能卡片和10-20个检索关键词K。以Key-Value的形式存入技能库，Key = Concat(问题, 关键词)，Value = 技能卡片

3.3 在线检索与注入

检索：使用 BM25（数学）或 Hybrid（BM25 + Dense Embedding，代码）检索 top-k 技能

注入：将技能卡片前置到Prompt中（Figure 13展示了标准模板）

轻量门控：Prompt中附带仲裁指令——"仅使用直接适用的技能；忽略无关或矛盾建议"

存在的问题&可以改进的方向：

1.痛点： TRS 必然引入额外的 Input Token 开销 。论文提到，如果检索命中率低或卡片过长，端到端的计算成本可能反而增加 。

可做工作： 设计一种“级联/按需检索（Cascade/On-demand Retrieval）”机制。训练一个极小参数的 Router，先判断当前问题是否是“常规简单题”。如果是，直接走短 CoT（如 Chain-of-Draft）；如果判断为“困难/高开销题”，再触发外部技能库检索。通过这种自适应阈值，在整个评测集上实现宏观 Token 消耗的进一步最小化。

2.原子技能的泛化与图谱化（Skill Compression & Knowledge Graph）：

  • 痛点： 当前是离散的 Key-Value 库，缺乏对技能之间关联性的建模。随着题库增大，特定问题的技能会变得冗余，论文提出需要研究如何将大量问题级技能压缩为少量通用技能 。
  • 可做工作： 将提取出的经验卡片构建为“技能图谱（Skill Graph）”。在离线阶段，利用聚类或图合并算法，将底层逻辑相同的卡片合并为高阶模板（Meta-skills）。在线检索时，沿着图的连通性召回，而非单纯的文本相似度计算。

3.另外可以考虑Skillreducer那篇中根据真实结果进行回补的方法来进行压缩卡片

4.对比型？对一个问题同时生成正确和错误的，然后定位错误点，找出关键问题。

Scaffolding, Not Stronger Reasoning:Diagnosing Skill-Card Retrieval for Mathematical Problem Solving

这是对上一篇论文的诊断，认为上一篇论文的工作只是给比较弱的模型提供了一个外部脚手架，没有让模型推理更强。对于好模型甚至有可能是负面提升。

列出的问题：

  1. 现有的 RAG 或工具调用评估体系大多只看“总体准确率（Aggregate accuracy）”和“词汇相似度（Lexical similarity）”。这种评估掩盖了检索内容的“相关性（Relevance）”与“严格数学适用性（Applicability）”之间的本质差异。强模型在接收到高度相关但不完全适用的外部提示时，容易被误导，导致原本能做对的题目反而做错（引入干扰项）。
  2. 检索相关性不等于技能适用性（Retrieval relevance \(\neq\) Skill applicability）。技能检索对于弱模型是雪中送炭的脚手架，但对于强模型，即便检索到 Top-1 的技能，若其不具备完全的数学适用性，不仅毫无增益，反而会成为导致推理崩溃的干扰项（Distractor）。

思考：

  • 虽然上一篇的结果被部分否定了，但成本下降也是不错的事。不过这个成本下降也是针对测试的数据集，对于开放域任务是否有不错的效果很难说。
  • 那我是该做继续做弱模型轨迹压缩相关的内容还是找一条路来解决强模型压缩负效果的问题呢？

备注：这篇我认为最契合的原因是因为它是结合skills且优化指标中有tokens消耗，其余的有些就是上下文压缩，有些就是跟skills自进化有关的、有的则是跟强化学习有关（Skill Reuse as Compression in Agentic RL）

TRS 的核心思想是实现一次范式转换：将“从头开始推理（Reasoning from scratch）”转变为“基于回忆经验的推理（Reasoning with recalled experience）”。

离线经验蒸馏（Offline Distillation）： 模型在解决复杂数学或代码问题时，往往会产生漫长的试错和纠路轨迹（长 CoT）。TRS 在离线阶段利用强大的总结模型，将这些冗长的成功或失败轨迹提炼成极其紧凑的“结构化技能卡片（Skill Cards）”。卡片包含五个字段：触发条件（Trigger）、操作（Do）、避免的陷阱（Avoid）、检查（Check）和风险（Risk）。这些卡片以键值对（Key-Value）的形式存储在外部库中。在线检索与注入（Online Retrieval & Injection）： 当面临新问题时，外层系统会检索最相关的 top-k 张技能卡片，并将其作为 Prompt 的一部分注入给闭源模型。此外，还会附带一个“轻量级门控指令（Lightweight gating）”，告诉模型“只使用直接相关的技能，忽略无关或矛盾的建议”。打破“效率-准确率”权衡（Breaking the Trade-off）： 以往压缩 Token 的方法（如强制要求简短输出的 Chain-of-Draft 或 TALE）在面对难题时会导致准确率灾难性下降。而 TRS 通过注入以前的“防坑指南”和“捷径”，不仅显著降低了模型输出思考 Token 的数量（从而降低了成本和延迟），反而还维持甚至提升了代码和数学任务的准确率。

但后续又有一篇叫 Scaffolding, Not Stronger Reasoning 的论文，对上面这篇TRS框架再进行了诊断。

认为上一篇论文的工作只是给比较弱的模型提供了一个外部脚手架，没有让模型推理更强。对于好模型甚至有可能是负面提升。

这篇论文结论要点总结：

  1. 评估范式的盲区：混淆了“检索相关性”与“规则适用性”
  2. 强基座模型面临的“部分适用性”陷阱（Distractor Effect）
  3. 无效规则注入导致的“双重 Token 损耗”

列出的问题：

  1. 现有的 RAG 或工具调用评估体系大多只看“总体准确率（Aggregate accuracy）”和“词汇相似度（Lexical similarity）”。这种评估掩盖了检索内容的“相关性（Relevance）”与“严格数学适用性（Applicability）”之间的本质差异。强模型在接收到高度相关但不完全适用的外部提示时，容易被误导，导致原本能做对的题目反而做错（引入干扰项）。
  2. 检索相关性不等于技能适用性（Retrieval relevance \(\neq\) Skill applicability）。技能检索对于弱模型是雪中送炭的脚手架，但对于强模型，即便检索到 Top-1 的技能，若其不具备完全的数学适用性，不仅毫无增益，反而会成为导致推理崩溃的干扰项（Distractor）。

另外我看到最近也多了一些做Skill相关的数据集的，我看到有侧重验证Skill进化能力的，有侧重验证技能检索能力的（SkillRet），有评估llm智能体技能生成能力的（SkillGenBench、SkillEvolBench）

我想到的设计：

  1. 比如对于一个复杂任务如果像之前这两篇选择了许多skills，可能其中有一部分skills是互相覆盖的，那我可以考虑在选择skills的时候在第一个之后就考虑边际效应，对于第一个skill后的每个skill的选择都让模型根据已选择的评估边际效应，剔除重复的skill。
  2. 基于Scaffolding，设计一个更复杂的评估器来评估选择的skill是否适合被选入

复现TRS

论文流程：

a) 方法流程总结 (Pipeline) TRS 框架是一个无需训练的、与黑盒API兼容的即插即用流程，分为离线技能构建和在线检索注入两个阶段。

  • 步骤1：生成推理轨迹 (Offline)。给定源问题 \(q_i\) 与答案 \(a_i\)，使用推理模型 \(\mathcal{M}_r\) 生成包含试错的完整推理轨迹 \(\tau_i\) 和预测结果 \(y_i\)，并评估其正确性 \(c_i\) 。
  • 步骤2：经验蒸馏与提炼 (Offline)。使用更强的总结模型 \(\mathcal{M}_s\) 处理记录 \((q_i, a_i, \tau_i, y_i, c_i)\)。若 \(c_i=1\)，提取成功的核心模式；若 \(c_i=0\)，提取避免陷阱的修复方案。
  • 步骤3：结构化卡片构建 (Offline)。将提炼内容压缩为标准化的技能卡片 \(s_i\)（包含 Trigger, Do, Avoid, Check, Risk 五个维度），并生成 10-20 个检索关键词 \(K_i\) 。以 \((x_i \rightarrow v_i)\) 的键值对形式存入库中，其中键 \(x_i\) 由 \(q_i\) 和 \(K_i\) 拼接而成。
  • 步骤4：在线检索 (Online)。当遇到新问题 \(q\) 时，使用检索引擎匹配并召回 Top-\(k\) 个最相关的技能卡片。数学任务默认使用 BM25 稀疏检索（\(k=1\)），代码任务默认使用 BM25+Dense 的混合检索（\(k=5\)）。 【在计算 BM25 分数时，系统把 question、heuristic 和 keywords 全部拼接成了一篇大长文。】
  • 步骤5：提示词组装与轻量门控 (Online)。将检索到的技能卡片前置于用户查询 \(q\) 中，并附带一条轻量级的门控指令（Instruction），要求模型“优先使用最直接适用的技能，忽略不相关或矛盾的建议，保持推理简洁”。模型直接输出最终答案。

b) 模块功能分解

  • 生成器 \(\mathcal{M}_r\)： 提供原始的解题语料（含成功与失败的弯路），并在最终推理时作为执行器。
  • 总结器 \(\mathcal{M}_s\)： 负责数据降维与泛化，将冗长的、带具体数字的特定实例逻辑抽象为普适性的技能描述，并强制符合 Schema 规范。
  • 技能库与检索引擎： 充当模型的外部程序化记忆区，BM25 捕捉表面符号/公式特征（适合数学），Dense Embedding 捕捉深层语义（适合代码）。

c) 核心算法与公式解释

  • 正确性评估： \(c_i = Eval(y_i, a_i)\)。这是一个判别函数，用于区分模型产出的是“成功经验”（提取正确路径）还是“失败经验”（提取反面模式与修复方案）。
  • 增强索引键： \(x_i = Concat(q_i, K_i)\)。将原始问题与总结器生成的抽象关键词拼接。这能显著提升稀疏检索（如BM25）的召回率，同时保持索引的人类可读性。

与其他方法对比

a) 本质不同 主流方法（如 TALE、CoD）主要在“限制当前推理配额”或“压缩当前提示”上做文章，本质上仍是孤立地处理当前问题（Blank Slate）。TRS 的本质是“跨任务的经验复用”，通过外部注入已经证实的有效路径，替代模型的内部搜索树。

b) 创新点

  1. 同时蒸馏成功经验与失败模式的修复（Anti-pattern correction），将其抽象为规范化卡片。
  2. 将“发现逻辑”与“执行逻辑”解耦，离线承担高昂的探索成本，在线享受低廉的查表执行成本。

c) 适用场景 适用于具备明确推理路径、依赖启发式规则且难以通过穷举解决的高难度领域，如复杂数学推理（竞赛级）和竞技编程。对于无需复杂推理的短文本分类任务，该方法会造成不必要的成本增加且收益随机。

实验设计

a) 实验设计

  • 数据集： 选取 DEEPMATH-103K (数学) 划分 93K 用于建库，10K 测试；选取 NEMOTRON (代码) 过滤后保留 26.6K 建库，1K 测试。
  • 评价方式： 数学使用精确匹配 (Exact Match)，代码采用本地沙盒编译执行 (pass@1)。按基线模型处理各题所需的 Token 数（\(\theta\)）进行难度分层测试。

b) 优势最明显场景 优势在高难度子集和较弱模型上尤为显著。难度越大（模型需要“绕弯路”思考的时间越长），通过直接注入技能卡片节省的无效试错 Token 就越多，收益放大效应明显。此外，外部竞赛数学题集（如 AIME 2024 I）验证了技能跨数据集迁移的有效性。

c) 局限性分析

  1. 失败案例分析不足： 当前缺乏对“何种错误最容易被技能蒸馏纠正”的系统性研究，对细粒度失败动态的捕捉仍不够。
  2. Prompt 膨胀风险： 如果召回策略不佳或输入 Token 价格极高，技能卡片的注入可能会导致提示词过长，从而抵消减少输出 Token 带来的成本收益。
  3. 弱验证域表现未知： 实验集中在有自动化评测机的数学和代码上，对于无法严格形式化验证（Weakly verifiable）的开放领域，其有效性尚未充分证明。

一些小设计

  1. 检索到的技能可能部分不相关或相互矛盾。因此，我们采用了一种简单的处理方式：只使用那些可以直接应用的技能，忽略那些不相关或相互矛盾的建议。为防止提示内容过于冗长，我们采取了两项措施：(i) 为每张卡片设定一个预算限制，即只能使用有限的提示内容；(ii) 按照检索得分，只保留排名靠前的 k 条提示内容。关于这些限制条件的具体效果，我们将在第 6 节中进行详细分析。

Skill Self-Play: Pushing the Frontier of LLM Capability with Co-Evolving Skills

想法：这篇文章利用已有的稳定的Skill来生成新的Skill；方法的目的在于提升任务的成功率而不是减少Tokens消耗；Skill用在小模型上准确率似乎更容易提升；开源

痛点：

  1. 环境受限（Environment-bound）：依赖外部验证器（如代码执行器、游戏模拟器）能提供可靠奖励，但受限于预定义环境，任务空间狭窄，模型无法泛化到更广泛的开放性任务。
  2. 无引导生成（Unguided Generation + Post-hoc Filtering）：无约束的任务生成极易产生格式错误或过度拟合简单模板的低质量任务。事后过滤（如格式检查）是“被动”的，无法主动引导生成器产出高可用、逻辑一致且多样的任务模式，导致随迭代积累的误差引发“合成数据崩溃”。

方法：

有三个机制决定了它不重蹈覆辙：

第一，双流生成。 一条是"技能流"，按技能出题，注入结构先验；另一条是"开放探索流"，不给技能约束，专门去探新路。只走技能流会过拟合退化，只走探索流会崩塌，两条流按比例混合（α=0.5）才能又稳又广。

第二，门控课程奖励。 出题者的奖励是 1{任务有效} · (1 - 2|成功率 - 0.5|)。后半段是"中等难度"目标，把任务锚定在解题者的学习前沿（成功率 0.5 附近最理想）；前半段的"任务有效"硬门控是关键--它直接砍掉无效任务，防止出题者靠生成"无解难题"来作弊刷分（reward hacking）。

第三，技能库会进化。 每轮做三件事：从失败轨迹里Refine（改写已有技能）；淘汰一直只产出简单题的Prune（饱和技能，前沿奖励低于 γ_prune）；从开放探索流里把高价值新任务Induce成新技能（过"完整性 + 新颖性"双重过滤）。5 轮下来，每轮新增约 20 个技能包，活跃技能涨到 86 个，有效技能（指数化香农熵）涨到 46 个。

实验配置

1. 评测基准 (Benchmarks)

  • 工具调用 (Tool-call)：
    • API-Bank (Level 1-3)：测试多轮对话下的工具选择与参数对齐。
    • BFCL (4个跨领域子集)：包含 JS、Python、Java 等，测试跨规则泛化能力。
  • 逻辑推理 (Logical reasoning)：
    • ZebraLogic (Small 至 X-Large 四个难度)：测试严格的网格逻辑演绎与全局约束满足能力。

2. 参评模型 (Models) 实验覆盖了从 3B 到 14B 参数量的五个主流开源基座（自对弈中的出题和做题模型均由同一基座初始化）：

  • Qwen3 系列：Qwen3-4B-Instruct、Qwen3-8B。
  • Ministral-3 系列：Ministral-3-8B-Instruct、Ministral-3-14B-Instruct。
  • Granite 系列：Granite-4.1-3B。

3.指标：正确率，没有减少tokens消耗的

作者对优化智能体做出的38次有效“改进”操作进行了逆向统计，得出的结论：

  • 移除技能 (Remove Skills)：发生16次，是带来正向收益最核心的操作。 清理掉偏离主题或引起歧义的技能，能同时提升通过率和降低成本。
